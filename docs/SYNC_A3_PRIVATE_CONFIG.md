# SYNC-A3 第六阶段：私有有效配置与外部输入协调

更新：2026-11-08（Asia/Shanghai）。本阶段隔离实现/恢复检查通过，**A3 整体仍进行中**。当前任务见 [TODO](../TODO.md)，前序见 [保存协调](SYNC_A3_COORDINATION_PROTOTYPE.md)、[设备来源](SYNC_A3_HOST_PROTOTYPE.md)和 [双端原生私有存储](SYNC_A3_NATIVE_STORAGE.md)。本轮没有接入正式插件或新增真机测试。

## 问题与本轮结果

此前协调器只能向具有条件写保证的文档适配器保存；外部写者未排除时，真实 data.json 适配会暂停回写。现在本机有效配置可保存在**同一条私有接受/恢复日志**，协调器直接向该私有文档保存设置和 UI；外部 data.json 作为待校验输入。无需给 OS/云同步写者虚构 CAS，也不用同步文件保存本机身份或凭据。

`src/sync/persistence-prototype.mjs` 新增 local-document 事件与条件保存、原备份、历史版本接口；`src/sync/private-config-prototype.mjs` 实现有效配置投影与外部输入协调；原协调器继续保存独立草稿/pending。三方合并提取到 `settings-merge-prototype.mjs` 共用，原 29 项协调检查保留。

新增 **44 项隔离配置检查**和 **21 项签名真实磁盘检查**通过，后者含 **16 次实际子进程退出**。默认 `npm test` 构建 + **19 脚本通过**；原三套磁盘 65/53/12 项与 23/19/6 次退出在本轮复跑通过。同步细项共 **116 + 29 + 40 + 44 + 65 + 53 + 12 + 21 = 380**；进程退出 **64 次**已包含在检查数内，不再另加。双端各 18 项原生探针保留其历史范围，未在本轮重跑。

## 同一恢复日志中的条件保存

会话新增接口：

- `getLocalDocument()` / `compareAndSetLocalDocument(expectedVersion,data,{initialBackup})`：有效文档与事件版本条件保存。
- `getLocalDocumentBackup()`：读取首次完整原插件 JSON 备份。
- `listLocalDocumentVersions()` / `readLocalDocumentVersion(version)`：仅按已验证日志内的版本引用访问历史，不接受任意文件路径或 blob 摘要作为授权。

只有会话已有可靠接受状态后才能创建私有文档；首次写入必须提供原始 JSON 备份。备份和配置正文各自保存为有界内容摘要 blob，再写小型 local-document 事件，含 previous 文档版本、正文与原备份引用。后续不能更换原备份；未知/损坏引用和日志链停止恢复，不用空设置补齐。

文档版本使用配置提交事件的摘要，包含整条日志的因果链；独立草稿事件不会改变文档版本。A→B→A 也会产生新版本，旧 CAS token 不能复活；同一有效正文的幂等重试不多写事件。文档和草稿使用同一个会话写队列，但保存各自的字段，不互相整份覆盖。

设备绑定包装仍对事件/正文做 HMAC，本机最高日志进度锚覆盖新的配置提交事件；不是另外建一个没有锚保护的“配置缓存日志”。配置事件可以与已暂存布局事务交错，重启仍从正确的旧接受基线恢复原布局操作。

首次备份保留整个原 JSON，包括未知字段、旧布局和复制来的标记；这些标记不会因此成为本机接受凭据。私有有效文档不存 layoutOverrides，读取时从当前接受快照投影；版本 token 同时绑定配置事件与接受 fingerprint。保存方不能把草稿或外部布局塞进已接受缓存，接受改变会让旧 token 失效；提交窗口变化保留已写设置，但不确认过期缓存。

## 私有投影接口与输入范围

`createPrivateConfigProjection({session,validateSettings,getExternalEpoch,checkpoint})` 要求显式提供已有设置校验器与外部变更代次来源；没有默认“永远不变”的代次用于正式外部输入。当前测试中常数 0 只代表由测试控制、没有 OS 文件写者的夹具，正式宿主仍须在外部回调/读取流程中维护真实计数并核对。

`open()` 可返回 initialization-required；`initialize({sourceData})` 在明确引导后建立首份有效配置与原备份。已有文档时重复引导不重导入，更不会因新传入的坏配置覆盖/阻止恢复已存在的有效文档。初始 JSON 尚未通过设置校验时不创建假有效配置，也不修改原文件；既有加入流程的原插件备份仍保留。当前接口接收已解析的 JSON 对象，外部文件解析/缺失/半写错误由后续宿主读取层保留并暂停，不能把解析失败传成空对象初始化。

`documentStore.read/compareAndSet` 直接接入既有 `createSettingsCoordinator`。设置/UI 正常保存不需要 data.json 写权限，也不受同步工具正在改它影响；无 saveData、adapter.write/copy 或网络依赖。设置版本只明确支持旧缺省或 settingsVersion=1；未来版本作为无效外部输入保存，不能静默降级。

## 外部输入先记录，明确选择后采用

`observeExternal(sourceData,{epoch})` 捕获输入副本、规范摘要和完整结构化原文，校验 settings/pipeline，记录最新待协调输入；此时有效配置不变。相同规范 JSON 不重复消耗事件。只有 UI/布局/其他非设置字段改变时记录为 ignored-nonsettings，不把它们用于覆盖本机 UI 或接受布局；原文仍可通过历史版本读取。

正式宿主应先捕获 epoch，再读取本插件文件，最后显式传入该 epoch；读取期间出现通知就重读，不能等文件已经读完后才为旧数据打上最新代次。省略参数取得调用时代次只适用于测试控制的同步输入，不能替代真实文件读取证明。此模块既不读取 data.json，也无法替调用方证明输入文件仍当前，实际读取/通知绑定留待宿主接入验证。

新通知可更新最新输入指针，旧输入仍留在原私有版本中，`history({before,limit})` 每页最多 20 条，`readHistory(version)` 可回查具体副本。没有删除旧 blob、截断日志或自动 GC。历史未知版本查询不允许读取任意内容，也不会损坏当前会话；真实存储校验失败仍停止并要求重开。

`reviewExternal(id)` 按外部基线、外部新设置、已保存本机设置生成三方合并预览。数组按整个字段处理；删除和 JSON null 保持区别；无关本机修改和未知 owned 字段保留。它不会悄悄把正在编辑的设置草稿当作已提交值，草稿仍由原协调器保留。

`resolveExternal(id,{choice})` 支持：

- merge：只在所有字段能合并时提交；同字段不同值返回 review-required，保留本机值、外部输入和草稿。
- keep-local：明确保留当前本机设置，记录该输入已审阅并推进外部基线；不删除原输入。
- use-external：明确采用校验后的 settings/pipeline；不改本机 UI、顶层未知字段、设备来源或接受布局。

无效/未来设置版本保持 invalid-external，允许独立保存本机 UI，不通过“保留本机”把坏输入伪装成有效配置。下一份有效输入可继续协调，旧坏输入在历史中保留。选择完成后相同输入不重复导入。

未保存草稿若和新有效配置无关，之后保存可保留两边变化；若同字段冲突，原协调器保留草稿并返回审阅要求。外部采用不清除布局编辑草稿，也不绕过编辑期间的接收暂停。

## 重开与变化窗口

进程重开后，待协调输入和草稿都能恢复，但外部采用必须先由当前宿主重新读取并 observe 同一输入。仅靠持久的旧 id 不会获得“文件仍当前”的证明，返回 read-external-again。如果来源代次已变化，观察/提交前均暂停；最新输入取代旧 id 后，旧选择不能冒用为当前选择。

在最后提交窗口内发生新变化，已可靠提交的明确选择不假装回滚；返回 applied-deferred，调用方须重新观察外部输入后再决定界面应用。有效配置改变由结果的 effectiveChanged 标示；正式宿主还要取消过期交互、推进结构/配置 epoch 并按需要重建图谱，这部分不在本轮接入范围。
