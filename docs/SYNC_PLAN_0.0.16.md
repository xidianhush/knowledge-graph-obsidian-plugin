## 1. 用户已决定的目标

- 已支持的 PC 与 Apple 移动端，一端修改图谱，其他端能得到相应修改；双向、多设备，不固定 PC 为主端。
- 本轮只规划和交接，开发由下一位智能体完成。Android 不进入 0.0.16 实现和验收范围。
- 用户本人使用 **Nutstore Sync**；其他用户可能使用“Remotly Sync”及 Obsidian 官方 Sync。用户尚不清楚这些配置是否同步 `.obsidian`。
- README 和中英文 20 秒宣传片 v3 已获用户明确验收：“就这样，awesome”。保留文案、视觉、节奏及素材，不以同步开发为由重做宣传内容。

下面的共享范围、存储路径与冲突体验是**技术建议，不能冒称用户逐项确认**。下一位可先推进调查和合成测试，重要体验差异在候选中交用户判断。

## 2. 建议结论

**复用现有同步工具搬运文件，插件管理可共享的布局数据、应用更新和处理冲突。** 不另建账号、服务器、云数据库，不直接调用坚果云 WebDAV，不读取其他同步插件的凭据，不把用户绑定到某个服务。

推荐把共享布局放在 vault 内一个专用的**普通目录**，例如 `Knowledge Map Sync/`，不用点或下划线开头；此目录名与文件格式先经 `SYNC-A1` 实测定稿。这能避免把“必须同步整个 `.obsidian`”作为使用前提，也兼容 PC 和 iPad 使用不同 Obsidian 配置目录的情形。

共享文件建议采用**不可变的布局变更记录**，每次提交使用唯一文件名；避免所有设备反复覆盖同一个完整 JSON。收到的记录取并集，按因果关系合并。并发修改同一布局组时保留冲突版本，让用户选择；不以设备时间戳静默丢弃另一版。先完成小型合成原型与 Nutstore 实测，再冻结协议。

代价是文件数量、首次扫描与历史保留成本。`SYNC-A1/A2/A6` 必须测量这些成本；若实际工具不适合小文件记录，下一位须提出等价的无静默丢改动方案再调整，不用“整份最后写入覆盖”偷偷降低目标。0.0.16 不承诺多人实时协作、逐帧同步拖动或 App 退出后仍能自行联网。

## 3. 为什么不能只同步现有 data.json

当前源码核查（2026-11-08）：

- `src/plugin.js:onload` 只在启动时 `loadData()`，保存 `savedData`、`pipelineSettings`、`graphSettings`，由 `createLayoutStore` 保持布局内存。未实现 `onExternalSettingsChange()`。
- 布局、设置共用 `settingsSaveQueue`，布局保存用 `{...this.savedData, layoutOverrides: layout}` 写整份 `data.json`；`saveGraphSettings` 也会合入内存中的布局和 UI。此队列只能协调**同一个实例**。
- `src/adapters/obsidian-native.js:createNativeUiStorage` 也写同一文件。外端更新未载入时，本机仅折叠图例或保存设置，也可能把过期布局写回。
- `src/core/layout-state.js:createLayoutStore` 的 schema3 `revision` 是本机递增序号，不能当作跨设备的全局版本或因果顺序；现有 owner/busy/undo/redo 同样不是跨端锁。
- schema3 已存父级局部位置与相对半径，适合不同屏幕复用；`groups` 与 `structures`、路径迁移及结构摘要校验应复用，不能改用屏幕像素坐标。
- Vault 的普通文件事件不等于 `.obsidian` 设置变更事件；不能假定监听笔记 modify 就能捕获插件数据变化。

官方 API 的 `Plugin.onExternalSettingsChange()` 自 Obsidian 1.5.7 起提供，明确用于外部修改 `data.json` 后重新载入。本项目最低宿主 1.6.7 不因该回调本身需要提升。它是可用的配置入口，**不是**同步传输服务，也不能补回服务已覆盖掉的历史内容。核心布局建议通过专用共享目录传输；此回调用来防止本地缓存/设置被外部覆盖后继续盲写。接入时须保持未保存设置草稿。

## 4. 共享边界与前置条件

建议 0.0.16 的必做共享内容：文件夹、笔记、标题的手动排列；用户重置布局的结果；撤销/重做所产生的新布局结果。拖动完成后提交一次，不把每帧鼠标/触摸位置发成文件。

笔记正文、标题和 wiki-link 的编辑仍由用户现有笔记同步工具传递，插件收到后重建和协调布局；本插件不编辑或复制正文。自动生成的图谱、渲染缓存、预览内容、选择、平移/缩放视角、会话撤销栈不进入布局同步。语言、面板/图例状态、性能和预览预算建议保持设备本地；include/exclude/remap 等建图设置是否共享仍是产品选择，不把“同步布局”擅自扩大为“覆盖各端所有设置”。不同配置导致无法应用某组时应说明原因并保留原记录。

前提：同一逻辑 vault、相同笔记相对路径及身份语义，各端使用兼容插件版本；共享目录和 JSON 文件确实双向传递。不要求绝对路径、vault 显示名、屏幕尺寸相同。只有传输、依赖和冲突已解决后才承诺布局最终一致，不能保证同步服务的秒数或 iOS 后台运行能力。

启用同步时明确共享目录用途与数据范围。布局记录可能包含笔记路径、标题身份与结构摘要，**并非不含个人信息**；不含正文片段、嵌入内容、凭据或遥测。用户使用的同步工具决定传输、加密、保留和费用。本插件只能显示“本机记录已保存 / 已读取其他设备更新 / 等待依赖 / 有冲突 / 失败”，没有服务端回执时不能显示“云端已同步”。

## 5. 先验证真实传输链路（SYNC-A1）

先记录 Nutstore Sync 的实际版本、PC/iPad 宿主版本、双向模式、过滤/大小限制、JSON 支持和两端是否同一远端目录。不读取 `data.json` 中的 WebDAV 密码或其他凭据；由用户在工具界面确认必要配置。

在**独立合成测试库**创建普通目录下的随机 JSON 哨兵：PC 写入→通过原工具同步→iPad 读到；iPad 再写一个不同名哨兵→PC 读到。记录事件能否在前台被察觉，以及后台恢复/重开后是否补读；测试正常同步、离线、重复与乱序到达。不要将哨兵写进日常库，或为测试切换为“覆盖云端/还原本地”的镜像策略。

兼容验证顺序：

1. **Nutstore Sync：首要真实链路。** 官方说明支持桌面/移动、双向与单向/镜像、过滤和大小限制，但不能由此推定用户当前 `.obsidian` 或 JSON 设置。
2. **“Remotly Sync”：待确认准确插件 ID/版本。** 不自动等同于 Remotely Save。官方社区当前 `remotely-sync` 条目名为 NoteHarbor Sync，仓库 `zenyyxz/remotely-sync`；也可能用户指 `remotely-save`。两者分别记证据，未确认时保持待核实。
3. **Obsidian Sync：兼容目标。** 普通目录 JSON 的文件类型选项与排除目录需要在两端核对；不要求用户改买官方 Sync。没有账号或测试设备时写“未实测”，不能把文件镜像模拟当作服务通过。

第三方同步只传 Markdown、排除了 JSON 或专用目录时，先说明必要配置；不静默把操作记录伪装成 Markdown 笔记。不同工具不必共用一个真实远端；测试每条链路时独立，避免多个同步引擎同时写同一测试库。

## 6. 协议与一致性建议（SYNC-A2）

**传输协议版本与布局 schema 分开。** 2026-11-08 SYNC-A2 纯核心与资源验证完成后，实现契约定稿为 [SYNC_PROTOCOL_V2](SYNC_PROTOCOL_V2.md)：`Knowledge Map Sync/v2/<vault-id>/ops/<operation-id>.json`，操作级 structures 去重，布局 schema 仍为 3。下文保留规划取舍，字段/目录/预算及失败恢复顺序以该契约为准；技术定稿不代表已接运行包或通过产品/真机验收。共享目录是权威的布局变更集合，`data.json.layoutOverrides` 可作为物化缓存与关闭同步后的本地数据，不能同时成为另一套不受控的共享真相。

建议记录至少包含：协议版本、共享 vault 标识、操作 ID、因果前驱、操作种类、布局组键、完整组记录与必要的 structure 身份信息、多组操作的事务边界。设备标识只用于诊断，不做账号标识或绝对路径；操作 ID 必须在复制设备配置后仍不会碰撞，不依赖时钟或 `revision`。同一 ID 不同内容要报损坏，不覆盖；内容校验不等于来源认证。

共享 vault 标识首次创建后经同一共享目录传播；另一端已经有不同标识时提示连接/导入，不能自动把不同库合并。首次加入设备应先扫描已有共享记录，再决定导入自己的旧布局；空布局不得清空其他端已有数据。不同设备各有旧布局时分别保留，按同样冲突规则处理；迁移前保留本地备份，避免每次启动重复导入。

因果前驱要表达用户本次操作实际基于的布局；“见过文件”不等于“已经应用该布局”。允许记录与前驱/结构文件乱序到达，依赖未齐时保持待处理。不用墙上时间判定新旧，不采用 JSON 文本三方合并坐标或只按数字 revision 取最大值。

**最小合并单元为一个父级下的完整布局组。** 一次拖动可能让兄弟避让，不能只合并被拖节点的 x/y；一次操作涉及多组时须维持事务整体。互不影响的组可以自动合并；同组具有明确因果继承关系时应用后继；并发同组保留两版并提示选择。冲突解决写新的记录，覆盖已选择处理的全部冲突头，不能只删一端文件。同组冲突未解决前，各端可继续显示各自已保存状态并明确标注“冲突未解决”，不宣称已一致。

重置要记录逻辑删除（tombstone），不能仅删布局文件，否则旧设备会把旧位置复活。建议“重置全部”覆盖**当时已知**的组，并发新增组另行保留/提示；此体验须用户验收。撤销只针对本地可理解的历史；外端修改同组后不能用旧 undo 快照覆盖它，必要时清空相关历史或拒绝并说明。若撤销已发布结果，须产生新操作而非删除历史。

笔记/目录改名、标题增删和记录晚到必须沿用保守身份校验。收到旧路径记录时不能仅因“当前没有该文件”永久删除；待内容同步/元数据就绪后重试，不能靠内容相似度猜对应。同步导致的自动 reconcile、缓存保存、启动迁移不能无限产生反向新操作；只把有明确语义的用户修改和已定义迁移发布到共享集合。

0.0.16 初版不自动清理共享历史，避免离线设备需要的前驱或 tombstone 被删。记录数/字节预算与冷启动耗时由原型实测决定；达到预算时保留本地修改并清楚显示同步暂停/待处理，不能静默丢操作。压缩、快照和垃圾回收后置，若不做就无法达到可用性能，应在实现前重评范围。不得假设同步服务提供原子远端 rename、事务、CAS 或永久不丢文件。

## 7. 实现接入与安全应用

- `src/plugin.js`：统一设置、UI、布局缓存写入协调器；补外部配置重载与生命周期管理；接入共享布局服务。保留现有 view、command、plugin ID。
- `src/core/layout-state.js`：加入受校验的外部状态应用能力，不能从外面直接改闭包数据；保留写失败回滚、owner/busy 互斥、schema1/2 懒迁移、schema3 结构共享与局部修复行为。
- `src/adapters/obsidian-native.js`：UI 保存不能把过期布局覆盖回去；视图状态继续设备本地。
- 建议新增纯核心协议/合并模块及 Obsidian 文件适配模块，分别测试。使用公开 Vault/Adapter API 与 Web 平台能力，避免 Node `fs`、Electron、桌面路径和第三方插件私有接口。
- 普通共享目录先验证 JSON 是否被 Vault 索引及发出 create/modify/rename/delete；能监听则合并扫描、防抖、重试。若 JSON 不进入索引，使用 Adapter 列举/读取和前台补扫，不能依赖未公开的底层事件。启动、重新打开图谱和前台恢复后补扫；前台低频补扫是否必要由实测决定，不在 iOS 后台持续轮询。
- 部分写入、无效 JSON、未知 schema、缺前驱、重复事件、删除和服务生成的冲突副本都要容错；异常输入不替换有效布局，不把协议记录路径当作任意读写目标。限制长度、记录数、嵌套和坐标数值，拒绝路径穿越与非有限坐标。
- 远端更新到达时若正在拖动/提交，先排队，完成当前事务后重新判冲突；不要在手指下突然替换坐标。安全应用后保留当前设备视角和必要选择，不整页 reload 或强制跳回总览。
- 文件共享与笔记结构到达顺序不同：留待协调、给出状态，避免先判失效又回写“空布局”。已接受操作先可靠保存，失败不显示成功；重启能补发/补读，读入不触发写回风暴。
- 同步关闭后不删共享历史；本地布局可继续使用。回退 0.0.15 前备份数据，各端版本混用不支持双向编辑同步；旧版只会写本地 data.json，不能假定它理解新协议。

## 9. 必须覆盖的验证场景

1. PC 移动文件夹/笔记/标题，iPad 得到相同父级局部位置；反向同样成立。比较局部归一化坐标及身份，不比较不同窗口像素截图。
2. 接收端图谱已打开、未打开、App 重启、后台恢复；自动更新关闭时布局导入与重建的边界明确，不要求强制整页刷新。
3. 两端离线修改不同组，恢复后两份均保留；改同组不静默覆盖；同组冲突解决后各端最终一致。设备时间相差一天不影响因果判定。
4. reset-group/reset-all、撤销/重做与远端编辑交错；过期记录晚到不复活已知重置；并发新增组遵守已定义规则。
5. 拖动或保存中收到更新、设置草稿未保存、UI 图例频繁保存，不丢布局，不在交互中跳动。
6. 笔记/目录改名、标题增删先后乱序；内容未到、结构不同或 include/remap 不同，保留待处理或明确不兼容，不能错误套用到另一节点。
