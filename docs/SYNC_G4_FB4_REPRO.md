## 隔离复现与边界

脚本 `.local/sync-016/g4/repro-fb4.mjs`：从用户合成目录改名后的快照及两篇合成笔记建立两个全新宿主，通过正常新建/导入/采用建立接受状态，不注入用户设备身份或私有日志。使用生产graph/store/author/unified host/receiver；App/锁/共享文件为内存契约替身，不是iPad/Nutstore原生。

1. 两端同一接受基线；源端新增Fifth并自动发布。
2. 接收端仅先收到同样的新笔记正文，尚未收到布局记录，graphReady自动生成另一条结构记录。没有接收端手动布局编辑。
3. 源端删除Fifth并发布；之后交换全部共享记录。
4. 两端均返回shared-candidate-blocked；新增操作内容相同而ID不同，源端删除仅继承自己的新增分支。复现接受数3/2、共享4记录，原件保留，结果`reproduction.json`。该诊断断言当前缺陷存在，不加入默认成功门禁。

根因路径：每端在图谱结构不兼容时会独立发布协调结果；外部同步不保证笔记与布局操作的到达顺序。同一结构变化可被多端生成不同ID；即使起初新增结果完全相同，后续只沿一个分支的删除仍造成竞争。此前原生驱动控制了共享记录先到再改笔记，没有覆盖本路径。用户操作符合指南，不应要求通过控制服务文件顺序绕过。
