## R6 长历史耗时与容量

### 已有证据

[G8 测量记录](SYNC_G8_RESULT.md#r6-测量与待决定边界)来自 2026-11-21 的 G8 候选，main 为 b537a6d1…873ad9。它使用 Windows Node、生产 host/session 和合成内存存储适配器，交替编辑两篇合成笔记，形成两组布局及独立操作历史；不是 Obsidian 完整启动、实际磁盘备份或 iPad 基准。

- 首次计时：冷开回放 44.46 / 29.77 / 32.10 秒；备份并核验 91.85 / 132.50 / 86.57 毫秒；暂停时编辑拒绝 2.90 / 1.09 / 0.77 毫秒。后续恢复测量因脚本未先重开清除会话保存错误而停止，这一轮不能称整套完成。
- 完整补跑：409 条已接受独立操作时状态 paused。冷开回放 31.07 / 29.80 / 28.64 秒；备份并核验 98.76 / 91.63 / 83.67 毫秒，每包 420 个文件；暂停时编辑拒绝 1.28 / 0.78 / 0.85 毫秒。先重开清除错误后，明确轮换返回 rotated，预览及确认计时 278.40 毫秒；该计时不包含此前恢复备份导出。
- Node RSS 快照约 242 MiB，不能解释为峰值或 iPad 内存。409 条时触发暂停的具体维度没有独立归因，不能将 409 写成普遍可用上限。
- [测量计划](SYNC_G8_PLAN.md)在运行前定义了三次重复及调查线：冷开/备份各 30 秒、暂停编辑请求 5 秒。首次两次冷开、补跑一次冷开超过调查线；不能只引用补跑较快数据。调查线不是用户认可的等待时间标准。
- [iPad 小样本回执](SYNC_G8_IPAD_ACCEPTANCE.md#备份体感与草稿预览取消续报2026-11-21)记录恢复备份“体感一秒不到、没有卡住”。这是用户主观体感，不能替代近容量测量，也不与 Node 长历史结果矛盾。

本轮核对了这些仓库记录及[测量脚本](../scripts/sync_g8_benchmark.mjs)；原记录引用的 measurement-uApzHk/summary.json 及交付副本没有在当前工作区的对应路径找到，故没有重新读取原始计时 JSON 或重算统计。原历史目录不删除、不重建；上列数值按原报告引用。

### 当前仍适用的工程保护

只读核对当前源码，主要保护仍在：

- [共享输入预算](../src/sync/causal-prototype.mjs)：文件/操作预算 1024、单记录 2 MiB、单快照 8 MiB、扫描正文合计 32 MiB。[发现器](../src/sync/connection-catalog.mjs)及[操作扫描](../src/sync/attempt-history-prototype.mjs)按实际输入计数；重复、残片和适用发现扫描中的初始化记录也消耗预算。1024 不是保证可保存的有效编辑次数，更不是全库笔记数量上限。
- [私有存储预算](../src/sync/private-store-budget-prototype.mjs)：正常准入软线为 64 MiB / 4096 文件 / 3968 事件，硬保护为 144 MiB / 8192 文件 / 4096 事件。任一维度及其他记录/结构限制都可能更早拒绝。它们是保护线，不是用户可用空间保证或性能指标。
- [G6 容量证据](SYNC_G6_RESULT.md#新容量与空间证据)及[双端最终回执](SYNC_G6_FINAL_ACCEPTANCE.md)支持触顶保全、备份、明确轮换和旧端隔离的受控流程；其中填充 1024 份文件的用例验证文件数量保护，不能当作 1024 次真实编辑或实际 OS 磁盘写满。
- 不自动删除历史或抬高预算来放行。共享触顶与私有准入拒绝需要区分：后者可能使新编辑保存失败并恢复上次位置，不能笼统承诺“触顶后所有本地编辑仍能无限保存”。

### 当前判断

旧证据足以说明长历史可能明显变慢，且已有受控保全/恢复路径；**不足以承诺当前 e236fdc9 候选在某个规模内始终流畅。** 11 月 26 日的 G2 实际为两篇笔记、7 条布局操作、9 份共享文件，验证了保存/自动更新，没有覆盖长历史性能。

当前候选的完整工程回归不等于重新跑过规模基准。iPad 近容量的客观计时、峰值内存及 OS 可用磁盘仍缺证据；不能用 5000 个布局节点的结构护栏来推导支持 5000 篇笔记的性能。

## R7 坚果云限流与大量文件传输

### 已确认与未确认

[原问题 R7](SYNC_G8_REMAINING_ISSUES.md#r7--坚果云限流大量文件传输体验)记录 11 月 18 日用户遇到请求过频、PC 传输很慢。当轮有 1024 份共享原件及大量恢复备份文件；备份若被传输会增加工作量，但没有当时完整队列、排除规则和错误码，不能唯一归因于备份、插件或某个客户端。

[G6 最终回执](SYNC_G6_FINAL_ACCEPTANCE.md)确认后来手动传输、新 ID 到达、明确加入和双端一致已完成。11 月 26 日当前候选的小规模 Nutstore Sync 1.6.2 链路也通过用户复验，见[G2 最新结果](SYNC_G2_RESULT_2026-11-26.md)。这些成功不证明一般限流已消失。

本轮 G2 的实际预览及已用 iPad 包还表明诊断报告曾进入传输；“建议只传笔记和布局目录”不能写成插件已经强制排除其他文件。传输范围由外部工具决定，插件没有管理 Nutstore 网络队列或解除服务限流。

### 处置

沿用 11 月 21 日已接受的服务边界，保留原因未定的历史记录。G5 文档继续明确：笔记及 Knowledge Map Sync 由外部工具传输；完整恢复备份/兼容文件/诊断报告按其内容私有保管，备份目录与共享操作目录分开，实际传输清单需由用户核对。

不承诺云端固定完成时间、所有设备已同步或“限流已修复”；不为本项改账号、换客户端、清空远端或重试压测。若再次发生，新增独立场景记录工具版本、实际文件规模、完成/失败时间和脱敏错误，再定位。本轮不要求重新审批已经接受的 R7 风险。
